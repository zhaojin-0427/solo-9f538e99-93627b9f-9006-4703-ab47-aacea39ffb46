# 夜骑问卷核查工具集（Flask）

两个核查页：

1. **单份纳入核查**（`/`）：判断一份旧版答卷能否纳入新版夜骑分析——上传已答筛查项与
   当时展示/跳过的追问题号，系统自动判断哪些未答筛查项的补全与旧档相符，并以
   **最少的最坏补问题数**推荐电话补问题目。
2. **版号核查**（`/version-check`）：一台调查终端试用新版问卷后换回旧版，导出的整批
   答卷没有版号。填写旧版/新版两版配置并上传该终端的答卷批次（每批最多 2000 份、
   每份有唯一流水号），系统按“新版答卷在流水号上只连成一段（可为空）”核定每份答卷
   是**确定旧版 / 确定新版 / 待核**，并可下载只含“所有可行划分下都属新版”答卷的
   入仓 JSON。

## 一、单份纳入核查：判定逻辑

### 条件语言（至多 12 个是非筛查项）

- 变量：字母/下划线开头的标识符，如 `S1`、`X_1`
- 与：`AND` / `&&` / `&` / `与` / `且`
- 或：`OR` / `||` / `|` / `或`
- 非：`NOT` / `!` / `~` / `非`（支持紧贴写法，如 `非S1`、`S1或S2`）
- 括号 `( )` 与常量 `true/false`（也可写 `真/假`、`是/否`、`1/0`）
- 优先级：`非` > `与` > `或`，括号可改变优先级
- 示例：`S1 AND (S2 OR NOT S3)`、`非S1 与 (S2 或 S3)`

### 约束与补全

n 个筛查项共 2^n 种真值组合（n ≤ 12，即最多 4096 种），逐一枚举并过滤：

1. 已答筛查项：补全必须与答案一致；
2. 当时**展示过**的追问题：其展示条件在补全下必须为**真**；
3. 当时**跳过**的追问题：其展示条件在补全下必须为**假**。

过滤后：

- **无可行补全** → 旧档矛盾，页面给出一个极小矛盾核；
- **可行补全的纳入结论全部一致** → 直接判定“纳入/不纳入”；
- **结论仍有分歧** → minimax 计算“从当前起最坏还要问几题”，推荐补问题目。

每回答一题立即重新判定；若新答案与旧档冲突，拒绝该提交、提示冲突约束，并保留提交前
的结果与全部历史答案。

## 二、版号核查：核定逻辑

### 版本配置（旧版、新版各一份）

```json
{
  "items": ["S1", "S2", "S3"],
  "labels": {"S1": "夜间佩戴头盔"},
  "followups": [
    {"qid": "Q1", "condition": "S1 AND NOT S2"},
    {"qid": "Q2", "condition": "S3 OR S1"}
  ]
}
```

两版配置的筛查项、追问题集合与展示条件可以不同（例如新版改了 Q2 的跳题逻辑）。

### 答卷批次（每批 ≤ 2000 份，流水号唯一）

```json
{
  "responses": [
    {"serial": "101", "answers": {"S1": true},
     "followups": [{"qid": "Q1", "shown": true}, {"qid": "Q2", "shown": false}]},
    {"serial": "102", "answers": {},
     "shown": {"Q1": false, "Q2": true}}
  ]
}
```

- `serial`：字符串或整数，批内唯一；整批能按整数解释时按数值排序，否则按字典序；
- `answers`：已答筛查项（可空）；
- 逐题展示/跳过记录：`followups` 数组或 `shown` 对象二选一，每题必须显式给出
  展示或跳过；
- 也接受合并形式 `{"old_config": {...}, "new_config": {...}, "responses": [...]}`，
  完整示例见 `sample/version_batch.json`。

### 单份答卷与某版本“相容”的判定

一份答卷符合某版本，当且仅当：

1. 已答项都在该版本的筛查项内；
2. 逐题记录的题号集合**恰好等于**该版本的追问题集合（多记、少记均不符合）；
3. 存在一组未答项补全，使每条展示/跳过记录与该版本的条件求值一致。

实现上用位掩码可行域：n 个筛查项的全部 2^n 种取值编码为一个大整数的低 2^n 位，
每个条件预编译为“条件为真的取值集合”位掩码；一份答卷的相容性 = 若干位掩码按位与
之后非零，单份判定只需常数次大整数运算（2000 份 × 2 版实测约 30ms）。

### 连续段划分与三态

约束：**新版答卷在流水号顺序上恰好连成一段（可以为空）**。按相容性，每份答卷是
“必属旧版 / 必属新版 / 两可 / 两否”之一：

- 存在“两否”答卷，或“必属新版”的流水号跨度内夹着“必属旧版”答卷 → **整批无解**，
  页面逐条指出卡住划分的流水号（哪份与两版均不相容；哪份必旧却夹在必新的两个
  流水号之间）；
- 否则每份答卷得到三态：
  - **确定新版**：必属新版跨度内的全部答卷（任何可行划分都属新版）；
  - **确定旧版**：与新版不相容，或被必属旧版者隔断、无法并入新版段；
  - **待核**：存在属新版与属旧版的可行划分各至少一种。

### 入仓下载

下载的入仓 JSON **只收“确定新版”**（在所有可行划分下都属新版）的答卷，并携带
`state_version`：每次成功导入/更正构成一个已提交状态，状态号单调递增，下载文件里
的每份答卷与版号都来自同一个已提交状态（SQLite 事务快照保证）。

### 更正一份

按流水号提交更正后的完整答卷 JSON：

- **只重判这一份**与两版是否相容（2 次位掩码判定），其余答卷的相容位与内容不改写、
  不逐份扫描；可行性用索引上的 MIN/MAX/点查聚合完成；
- 受影响的版号随更正一并更新（例如某份待核答卷因相邻答卷变必旧而被隔断为确定旧版）；
- 更正若使整批无解：事务整体回退，指出卡住划分的流水号，**原数据与下载结果照旧**；
- 更正期间下载照常进行，下载内容始终是某个已提交状态的一致性快照；
- 导入同理：整批无解则批次不生效，原有批次与下载结果照旧。

## 三、启动方式

### Docker Compose（推荐）

```bash
SECRET_KEY=$(openssl rand -hex 32) docker compose up --build
# 浏览器打开 http://localhost:8000
```

不设置 `SECRET_KEY` 时使用开发默认值，仅适合本地试用。
批次数据存于容器卷 `nightride-data`（`/app/instance/versioncheck.sqlite3`），
跨重启保留；不需要持久化可删掉 compose 中的 `volumes` 段。

### 本地直接运行

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
flask --app 'app.app:create_app' run --debug
```

判定引擎与批次存储（`app/engine`、`app/batchstore.py`）仅依赖 Python 标准库，
未装 Flask 也可运行演示与引擎/存储测试。

## 四、测试与验证

```bash
# 全部测试（引擎 + 存储 + Web；无 Flask 时 Web 用例自动跳过）
python -m unittest discover -s tests -v

# 单份核查 CLI 演示
python scripts/demo.py sample/config_with_archive.json

# 版号核查 CLI 演示：导入核定 -> 入仓下载 -> 更正 -> 无解更正 -> 无解导入
python scripts/demo_versioncheck.py

# Web 冒烟（需先启动服务）
BASE=http://127.0.0.1:8000 scripts/smoke_web.sh

```

## 五、目录结构

```
app/
  app.py                 # Flask 路由（单份核查 + 版号核查页）
  batchstore.py          # 版号核查批次存储：SQLite 事务、更正回滚、下载快照
  engine/
    conditions.py        # 布尔条件词法/语法解析、AST 求值
    config.py            # 单份核查的配置与答卷模型
    solver.py            # 可行性枚举、极小矛盾核、minimax 最坏题数
    versioncheck.py      # 版号核查引擎：相容判定、连续段划分、三态分类
  templates/ static/     # 两个核查页
sample/                  # 示例输入（含 version_batch.json 合并批次）
tests/                   # unittest 测试（Flask 缺失时 Web 用例自动跳过）
scripts/                 # CLI 演示与 Web 冒烟脚本
```

## 六、交付核对：已实现 / 已验证 / 遗留项

### 已实现（本次新增：版号核查页）

- 两版配置填写（文本/文件/合并 JSON 三种方式），整批答卷上传，每批最多 2000 份、
  流水号唯一（重复/超限/缺记录均拒绝并说明）；
- 单份相容判定：已答项 ⊆ 版本筛查项、逐题记录题号集合与版本完全一致、
  展示/跳过记录存在可行补全；位掩码实现，2000 份 × 2 版约 30ms；
- 连续段划分三态：确定旧版 / 确定新版 / 待核，网页逐份可查（全量表格 + 按流水号
  查询详情），并展示必属新版区间与新版段可行范围；
- 入仓 JSON 下载：只收所有可行划分下都属新版的答卷，含 `state_version`；
- 按流水号更正：只重判该份与两版是否相容（有测试断言 judge 仅被调用 2 次），
  其余行不改写（有测试逐行比对）；受影响版号一并更新；
- 无解导入/更正：事务回退，逐条指出卡住划分的流水号，原数据与下载结果照旧；
- 更正期间可继续下载：SQLite WAL + 读事务快照，每份下载来自同一个已提交状态；
- 批次库存于 SQLite（默认 `instance/versioncheck.sqlite3`，可用 `BATCH_DB_PATH`
  覆盖），gunicorn 多 worker 共享；docker compose 一键启动。

### 已验证

- 引擎与存储 37 个 unittest 全部通过：流水号排序、解析边界（2000/2001 份、重复
  流水号、歧义记录）、位掩码与逐掩码求值 300 组随机条件交叉一致、judge 与暴力
  枚举参考实现 120 组随机配置零偏差、连续段划分 8 类场景、更正只动一行、
  无解回滚后整库逐行一致、快照隔离（读事务期间更正提交，仍读到旧状态）；

### 遗留项 / 已知边界

- 本机无 Docker 守护进程，`docker compose up --build` 未实跑；Dockerfile/compose
  已静态核对，且已用相同 WSGI 配置（gunicorn 2 worker）本地实测通过，建议在有
  Docker 的环境再执行一次完整构建冒烟；
- 批次数据按会话隔离（cookie 指向各自批次），未做多用户权限体系；定位为单调查员
  或小组内部分析工具；
- 流水号排序规则：整批全为整数样式按数值序，否则按字典序（混合批次的“自然序”
  未做更细粒度处理）；
- 更正以“整份替换”方式进行，不支持只改单题答案的增量补丁；
- 旧版 `scripts/smoke_web.sh` 第 3、4 步存在既有 bug（flash 被重定向后的再次 GET
